# ReelRoom implementation plan

## Approved scope and architecture

Build a browser-based, multi-participant watch-party application on the initialized React 19 / TypeScript / Tailwind / Express / tRPC / Drizzle / MySQL project. Keep visitors anonymous: assign a persistent browser participant ID, display name, and random 256-bit session token; store only the token's SHA-256 hash with that participant's room membership so an exposed public participant ID cannot claim host authority. Generate the first display name as `anonymous` plus a random eight-digit number (for example, `anonymous10298391`), migrate the old `Alex` default to a generated name, and preserve a name the visitor explicitly saves. Do not invent an account/login requirement. Serve Socket.IO over the existing HTTP server for low-latency room events, with its WebSocket-first transport and built-in reconnection/polling fallback. Keep ordinary catalogue and room-snapshot requests in tRPC/HTTP.

Persist room metadata, host/owner, participant identities and presence timestamps, authoritative playback state and monotonic revision, a playback-specific millisecond clock anchor (`TIMESTAMP(3)`), shared playlist entries, chat history, polls, and votes in additive Drizzle/MySQL tables. Treat the backend as the room authority: validate room membership, host-only media actions, bounded room capacity (10+; default admission ceiling 50), unique action IDs and monotonic room revisions; serialize conflicting state transitions; acknowledge actions and fan out accepted snapshots. On reconnect or late join, send a fresh versioned room snapshot before incremental events; discard stale/duplicate revisions. Buffer up to 100 unacknowledged mounted-room actions, then replay the same action IDs only after rejoin reconciliation; expire unsent intent after four minutes and show the user a warning. If the managed database is unavailable, surface a clear degraded/offline state rather than silently claiming durable state. WebSocket reconnect uses bounded exponential backoff, and Socket.IO fallback covers blocked upgrades.

For playback, represent the accepted state as `{source, position, playing, serverTimestamp, revision}`. Persist the anchor at millisecond precision. Keep room control events as the authority for direct MP4/WebM/Ogg files and YouTube watch, short, or embed URLs. Normalize and validate supported YouTube video IDs server-side, then use YouTube's official IFrame Player API on the client to play, pause, seek, report duration/current time, and correct drift. Accept the supplied `https://youtu.be/lo4bA4p3MBQ?si=kIuKwVv10g5ma5xR` as a YouTube source. Clients extrapolate position from server time and seek when error exceeds the correction tolerance; smaller HTML5-file errors may use a brief bounded playback-rate adjustment. Use estimated server time even when media metadata first loads. YouTube embed restrictions, autoplay/user-gesture policies, and buffering are distinct from command propagation; report them in the UI and latency notes. Attach preverified official or public-domain full-film source URLs to database movie rows only when evidence supports that label, retain the source page and rights notes, and leave the field empty when a safe full-film source was not found. Selecting a movie loads its saved URL automatically when present. Keep the host's source dialog as a fallback, including the supplied YouTube link; do not provide unauthorized copies or claim globally cleared rights for a source that has narrower jurisdiction.

Provide a responsive movie discovery catalogue stored in the managed database, with exactly 30 curated, source-checked titles split evenly between Hollywood and Bollywood (15 each). Normalize movie records and their multiple genres; expose industry and genre filters alongside mood/runtime filters and typo-tolerant fuzzy search. Store accurate poster images as project assets and show poster, title, release year, runtime, genre, industry, and a short synopsis in the Start Here shelf. Store an optional playable full-film URL plus its official/public-domain classification, evidence page, and rights note; attach it only where verified and explain missing sources without implying a catalog record is itself watchable. Selecting a record with a verified playable URL automatically loads it in the shared player. Use an idempotent seed command that inserts missing rows, preserves existing values, and backfills optional playback-source fields only when the existing URL, source classification, evidence URL, and rights note are all empty. Avoid external catalogue credentials. Rooms expose invite URL/copy and short room code. Collaboration includes presence, live chat, emoji reactions, a deduplicated shared queue, a multi-option group poll with vote updates, and explicit host transfer.

## Project structure

- `client/src/pages/Home.tsx`: discovery landing and create/join entry.
- `client/src/pages/Room.tsx`: room experience, shared player, media controls, presence and collaboration panels.
- `client/src/components/YouTubePlayer.tsx`: official IFrame API-backed player bridge that reports media time and obeys shared room state.
- `client/src/lib/realtime.ts`: typed Socket.IO connection, reconnect lifecycle, room event subscriptions.
- `client/src/lib/identity.ts`: persistent anonymous browser ID/token and generated display-name default.
- `shared/catalog.ts`: movie/catalog types, a hard 30-title maximum, source-provenance fields, and fuzzy-search helpers; movie records themselves come from MySQL.
- `server/catalog.ts`: public tRPC listing query for 30 database-backed movies and genre facets.
- `scripts/seed-catalog.ts`: idempotent catalog seeding; insert absent records and preserve existing edits.
- `shared/realtime.ts` and `shared/sync.ts`: typed room protocol, authoritative playhead estimation and drift-correction policy.
- `client/src/index.css`: ReelRoom design system and responsive room/discovery layout.
- `server/_core/index.ts`: mount Socket.IO on the existing Express HTTP server.
- `server/realtime/`: event protocol, room authority, validation, snapshot/reconnect and drift logic.
- `server/routers.ts` and `server/rooms.ts`: tRPC room creation and durable DB access.
- `drizzle/schema.ts` and additive migrations: persistent room, participant/session-token hash, playlist, message, poll/vote, normalized movie/genre entities, and optional verified film-playback URL plus provenance.
- `client/public/posters/`: locally served, accurate poster artwork for the curated Start Here movies.
- `scripts/latency-test.ts` and `server/realtime/store.test.ts`: repeatable local multi-client propagation and drift simulations.
- `docs/performance-and-failures.md`: test conditions, observed measurements, limits, thresholds, and failure/recovery behavior.
- `docs/movie-catalog-sources.md`: per-title metadata, poster references, playable source URL (if any), source-owner/public-domain evidence, and jurisdiction notes for the curated database set.
- `client/public/manus-routes.json`: current page routes (`/`, `/r/:code`).

## Performance evidence and failure contract

The product targets at least 10 simultaneous participants in one room, accepted control propagation below 250 ms at p95 on a local network, and corrected playback position error below 500 ms. The harness creates 10 real Socket.IO clients against the running local app/server, timestamps each accepted control and each participant's received revision, records sample count/p50/p95/max, and exercises concurrent actions, duplicate retries, disconnect/reconnect and late-join snapshot behavior. Clients estimate server clock offset from echoed join/heartbeat timestamps. Drift samples run every 1.2 seconds; errors over 500 ms hard-seek and 120–500 ms errors get a bounded, temporary playback-rate correction for HTML5 media. Identify OS, runtime, participant count, event count, and loopback topology. Sandbox loopback evidence is not evidence of a separate-device Wi-Fi LAN, broad Internet performance, media decoding/buffering, YouTube embed availability, or multi-instance production; label these limits plainly and do not claim unmeasured thresholds as achieved.

Failure behavior: reconnect with exponential backoff and resubscribe; immediately reconcile from the latest authoritative snapshot; ignore stale/duplicate revisions; reject non-host playback actions and invalid membership; make room mutation retries idempotent by action ID; cap and validate chat/queue/poll inputs; preserve accepted room state in MySQL across process restart; show offline/degraded feedback rather than silently falling back to nondurable room state when the managed database is unavailable. Presence uses server heartbeats/last-seen expiry. If YouTube disallows embedding, requires a viewer gesture, or is unavailable in a region, explain the issue and allow another supported link; do not imply the source itself was tested just because it was accepted. Deployment is one app-server instance unless a shared Socket.IO adapter/pub-sub layer is added; do not claim cross-instance fan-out. No test will delete or mutate existing user records; any test-room writes, if used, are isolated or explicitly test-only.

## Design system

- **Design Movement:** Contemporary independent-cinema editorial—an intimate screening room translated into a crisp streaming product.
- **Core Principles:** Focus the eye on the film; make shared presence warm and legible; keep controls immediate and tactile; disclose synchronization and connection health instead of hiding it.
- **Color Philosophy:** Ink-black and plum create a low-glare theater backdrop; soft ivory is reserved for essential reading; electric tangerine is ReelRoom's energetic action/brand color; muted mint marks healthy sync.
- **Layout Paradigm:** Asymmetric, film-first room canvas with a wide player rail and a narrow stacked activity column; discovery is a horizontally paced shelf-led editorial page rather than a centered dashboard grid.
- **Signature Elements:** Framed sprocket/film perforation motif; tiny live-sync pulse with measured status; authentic, locally served film posters with a consistent dark scrim and strong title/genre labels.
- **Interaction Philosophy:** Controls respond optimistically while showing the server-accepted state; host-only actions are clearly indicated; room events appear as lightweight, non-blocking live signals.
- **Animation:** Short (140–220 ms) ease-out transitions for panels and buttons; gentle pulse on live/sync indicators; reduced-motion preference honored; no looping motion competing with video.
- **Typography System:** Space Grotesk for headlines and expressive titles, Inter/system sans for interface/body, tabular numerals for time/status; strong compact section headings and readable small metadata.
- **Brand Essence:** “A better seat is a shared one”—for friends who want to find and watch something together without losing the little moments; **warm, quick, cinephile**.
- **Brand Voice:** Clear, playful, never needy. Examples: “Pick the plot. We’ll save you a seat.” / “You’re in sync. Let the good part roll.”
- **Wordmark & Logo:** A custom `reelroom` lowercase wordmark with two offset perforation dots forming a small play-frame at the left; not a default-font-only logo.
- **Signature Brand Color:** ReelRoom ember, a saturated orange-red reserved for primary actions and the live mark.

## Serving and dependencies

Use the existing project stack and its managed Server + MySQL resources. Add `socket.io` and `socket.io-client` as pinned project dependencies, keep browser URLs relative, use additive Drizzle migrations, and leave `/api/health` intact. Dev and production use the same Express-created HTTP server so Socket.IO attaches to the same origin/port. Load YouTube's IFrame API from the official embed origin at runtime; do not proxy, download, or host YouTube content. Do not introduce third-party secrets or external streaming APIs. Do not enable automatic publication; deliver the live Preview unless an existing authorized publication flow is explicitly established.
